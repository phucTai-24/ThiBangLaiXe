# Thi Bang Lai Xe Mo To - Master Delivery Plan, API Blueprint, and Swagger Testing Guide

## 1. Executive Summary

This project already has three strong inputs:
- a detailed requirement document defining the exam-learning product scope,
- a progress/report document describing business goals, architecture direction, and testing intent,
- and an actual backend repository that has started with ASP.NET Core Web API, JWT, Swagger, EF Core, SQL Server, and an initial authentication module.

However, the current implementation is still **far behind the documented scope**:
- the requirement/report documents define a complete exam platform with question bank, random exam generation, sample exams, wrong-question practice, critical-question practice, traffic signs, regulations, statistics, and role-based administration,
- while the current backend branch visibly exposes only `AuthController` and `WeatherForecastController`, with `AuthRepository`, `AuthService`, JWT setup, Swagger setup, and many generated model/DTO files but not a full domain API surface yet.

Therefore, the correct enterprise direction is **not** to keep coding feature-by-feature without structure. The correct direction is:
1. freeze the target scope,
2. cut out scope creep,
3. normalize domain modules,
4. define a stable API contract,
5. enforce response/validation/error conventions,
6. build Swagger-first,
7. make every module independently testable,
8. keep docs and code in sync.

## 4. Recommended Architecture

### 4.1 Solution structure
```text
src/
  ThiBangLai.Api/
  ThiBangLai.Application/
  ThiBangLai.Domain/
  ThiBangLai.Infrastructure/
  ThiBangLai.Contracts/
  ThiBangLai.Tests.Unit/
  ThiBangLai.Tests.Integration/
```

### 4.2 Layer responsibility
- **API**: controllers, Swagger, auth filters, API contracts
- **Application**: use cases, service orchestration, validation flow, business rules
- **Domain**: entities, enums, business invariants, domain services
- **Infrastructure**: EF Core, repositories, external services, file storage, email, logging
- **Contracts**: request/response DTOs, shared API models
- **Tests**: unit + integration + test data builders

### 4.3 Controller rule
Controllers must only:
- receive request,
- validate basic API shape,
- call application service,
- return standardized response.

No heavy business logic in controller.

### 4.4 Repository rule
Repository only:
- query data,
- persist data,
- not apply exam grading business logic.

### 4.5 Service/Application rule
Application service handles:
- exam generation rule evaluation,
- grading,
- wrong-question updates,
- critical-question result rules,
- dashboard aggregation coordination.

## 5. Standardized API Conventions

### 5.1 Response envelope
All APIs should return one unified shape:

```json
{
  "success": true,
  "message": "Operation completed successfully.",
  "data": {},
  "errors": null,
  "meta": {
    "traceId": "...",
    "timestamp": "2026-04-04T00:00:00Z"
  }
}
```

For validation/business errors:

```json
{
  "success": false,
  "message": "Validation failed.",
  "data": null,
  "errors": [
    {
      "code": "QUESTION_TOPIC_REQUIRED",
      "field": "topicId",
      "message": "Topic is required."
    }
  ],
  "meta": {
    "traceId": "...",
    "timestamp": "2026-04-04T00:00:00Z"
  }
}
```

### 5.2 HTTP status rule
- `200` read/update success
- `201` create success
- `204` delete success / no-content action
- `400` request shape invalid / business validation failure
- `401` unauthenticated
- `403` authenticated but forbidden
- `404` resource not found
- `409` conflict / duplicate / illegal state transition
- `422` semantically invalid exam rule set
- `500` unhandled system error

### 5.3 Pagination
```json
{
  "page": 1,
  "pageSize": 20,
  "totalItems": 250,
  "totalPages": 13
}
```

### 5.4 Audit fields
Every manageable entity should have:
- `createdAt`
- `createdBy`
- `updatedAt`
- `updatedBy`
- optional `deletedAt`
- optional `deletedBy`
- optional `isDeleted`

## 10. Swagger Testing Strategy

## 10.1 Swagger must be usable as the first QA gateway
Swagger should not be a decorative UI. It should be a daily working tool.

### Swagger requirements
- all endpoints tagged by module
- all request DTOs described
- all response DTOs documented with example payloads
- all auth-protected endpoints require bearer auth scheme
- all important error responses documented (`400`, `401`, `403`, `404`, `409`, `422`)

## 10.2 Swagger test sequence for the current backend
Because current code visibly has auth first, initial Swagger testing should be:
1. `POST /api/Auth/register`
2. `POST /api/Auth/login`
3. Copy JWT token
4. Click `Authorize`
5. Enter `Bearer {token}`
6. `GET /api/Auth/me`
7. `PUT /api/Auth/me`
8. `POST /api/Auth/change-password`
9. `POST /api/Auth/logout`
10. `POST /api/Auth/forgot-password`
11. `POST /api/Auth/reset-password`

## 16. Final Recommendation

If the team wants a project that looks enterprise, is easy to continue, and does not break when handed to another developer, then the key is not just “write more APIs”.

The key is to make the backend **predictable**:
- predictable modules,
- predictable response shape,
- predictable error handling,
- predictable role rules,
- predictable Swagger testing,
- predictable sprint order,
- predictable documentation.

The current repository is a workable starting point because the .NET 8 + Swagger + JWT + EF Core base is already there. But it still needs a strong architecture pass before expanding features. The safest path is to treat Auth as the first finished vertical slice, then deliver the rest of the system module-by-module in the order defined above.
